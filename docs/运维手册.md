# 运维手册

把"机器上跑着几个实例、它们的公网地址是什么、谁在排障"这套日常操作集中写在这里。
命令都是 `cochat`（Windows 上是 `cochat.exe`），下面统一用 `cochat`。

---

## 1. 我现在该把哪个地址发给对方？

```powershell
cochat --cur
```

```
pid      端口 公网地址                                 状态
12345    8080  https://xxx.trycloudflare.com           已连接            [cli]
         数据目录 D:\intercom\data
         命令行  D:\intercom\cochat.exe --port 8080 --tunnel-url https://xxx.trycloudflare.com
```

读法：

| 状态 | 含义 | 该做什么 |
| --- | --- | --- |
| `已连接` | 地址此刻真的能对外访问 | 直接把地址发出去 |
| `隧道未建立` | 服务在跑，但没有地址可用 | 起隧道，用 `--tunnel-url` 告知服务 |
| `隧道已关闭` | 用 `--no-tunnel` 明确声明没有隧道 | 改配置或另起隧道 |
| `无响应` | 进程在，但端口连不上 | 看日志 / `cochat --res` |

**"无响应 + 地址来自自述文件"要当心**：那个地址是上一次运行留下的，很可能已经死了。
宁可重起隧道拿新地址，也不要把它发给别人。

地址的来源会在方括号里标出来：

| 标记 | 含义 | 可信度 |
| --- | --- | --- |
| `[plugin]` | 内建隧道插件注册成功，边缘给的域名 | **最可信**，边缘已接受连接 |
| `[cli]` | 启动时 `--tunnel-url` 转述的地址 | 服务并不知道通不通，只记录 |
| 无标记 | 自述文件里的历史值 | 上次运行的残留，很可能已失效 |

## 1.5 内建隧道（推荐）

不用再手动跑 `cloudflared.exe`，隧道是主程序加载的动态库：

```powershell
cochat --tunnel                     # quick 隧道，自动申请域名
cochat --tunnel-token <连接令牌>     # 命名隧道（有固定域名时用这个）
```

要点：

- **插件必须在主程序同目录**（`cochat-tunnel.dll` 或 `libcochat-tunnel.so`），
  安装脚本会自动带上它。缺了插件不是故障，`/api/info` 会说"未启用"及原因。
- 新申请的 quick 域名通常要 **1–2 分钟**才解析得出来。这段时间打开会看到 530，
  等一会儿再试，别以为坏了。
- 排障时设 `COCHAT_TUNNEL_LOG=3` 能看到完整过程：注册域名 → 连边缘 → 注册成功。
- 隧道断了会自动重连（指数退避，最长 30 秒一次），不用手动干预。

## 1.7 管理面板（`/admin`）

面板在同一个端口上，浏览器打开 `http://127.0.0.1:8080/admin`，
走隧道时是 `https://你的域名/admin`。

账号**固定是 admin**，不能另建一个管理员 —— 面板的账号不是独立体系，
它就是你账号库里的 `admin`。

面板「运行概况」里的隧道读数取的是**插件此刻的真实状态**，不是启动参数：
绿色「已连接」+ 真实域名才算通；「正在连接」「已连边缘，注册中」「连接失败：…」
分别是不同阶段的失败点，比 `--tunnel-url` 那种静态声明可信得多。

| 想做 | 怎么做 |
| --- | --- |
| 第一次登录 | 看服务启动时打印的那串随机密码（只打印一次） |
| 改面板密码 | `cochat --passwd admin`，或面板「账号」标签里点「改密」 |
| 忘掉了 | 只能走 `--passwd admin`（命令行）。面板进不去时它仍然有效 |

常见误操作，全都被拦住：

```
cochat --del admin
  error: admin 是面板保留账号，不能删除（否则再也进不去 /admin）

cochat --un admin root
  error: admin 是面板保留账号，不能改名（源或目标都不行）
```

大小写和空格都算（`ADMIN` / ` admin ` 一样被拒），因为账号文件名本身就是小写的。

### 面板里的「重启」为什么会让页面短暂失联

面板就活在被它管理的那一个进程里。点重启时它是**先拉起新进程、再退出自己**，
而且先把手上的 HTTP 响应发出去再动手。所以你会看到：

1. 点「重启」→ 立刻提示「已发出重启」；
2. 页面转几秒连不上（旧进程正在退出、新进程正在绑端口）；
3. 刷新就恢复，连的是新 pid。

> 如果反过来（先杀自己再起新的），现场就是「点了重启，服务没了」。
> 这个顺序在 `src/restart.cpp` 里有两处刻意注释，改代码前先读那两段。

### 面板留痕

登录与账号操作都会进服务端日志，面板「日志」标签里也看得到：

```
[2026-11-14 17:04:43] 面板 登录成功 ip=127.0.0.1
[2026-11-14 17:04:43] 面板 新建账号 dave 成功
[2026-11-14 17:04:43] 面板 删除账号 eve 成功
[2026-11-14 17:04:43] 面板 重启实例 pid=6944
```

日志只留最近 500 行在内存里（不落盘）。要长期留存就把 stdout 重定向到文件或交给 journald。

## 2. 重启一个实例

```powershell
cochat --res          # 重启 pid 最小的那个
cochat --res 12345    # 重启指定 pid
```

它会：

1. 先确认该 pid 现在**仍然是 cochat**（pid 会被系统回收，误杀无关进程是最坏的错）；
2. 是 systemd 托管的 → 走 `systemctl restart <unit>`，保留 unit 的 `Restart=` 策略和环境；
3. 手工启动的 → 按**原命令行、原工作目录**重新拉起（Windows 上还会脱离当前控制台和 Job）；
4. 最多等 20 秒打印新实例真正对外服务的地址。

> 旧地址在重启这一刻就失效了。`--res` 之所以要等到新地址出来才返回，
> 就是为了不让你把死链发出去。

重启失败时它会说清楚原因（进程不退出 / 权限不足 / 替换进程立刻退出），而不是静默成功。

## 3. 改密码 / 核对密码

```powershell
cochat --passwd alice                     # 交互输入，不回显
cochat --passwd alice 新的密码            # 直接给（密码里可以有空格、中文）
cochat --passwd                           # 只报告账号库位置，不改任何东西
cochat --passwd --check alice 某个密码    # 只核对，不改
```

`--check` 会做**两件事**，缺一不可：

```
账号文件:          匹配
运行中的服务:      接受（已验证登录）
```

- `账号文件` —— 用文件里的盐现场算一遍哈希，看是否吻合；
- `运行中的服务` —— 真的用 `/ws` 发一条 `{"t":"auth"}` 登录，看服务收不收。

**为什么两个都要**：文件对了不代表服务认（改了账号目录、服务连的是另一个库、进程被锁定……）。
只报"文件匹配"会给人虚假的安全感。

| 输出 | 含义 |
| --- | --- |
| `接受（已验证登录）` | 文件和服务都认，可以用 |
| `拒绝（用户名或密码不对）` | 服务明确拒绝，密码错了 |
| `未能验证（…没有可用的服务）` | 服务没在跑 / 端口不对，**不算通过**，退出码 1 |

改完立即生效：服务按账号文件的修改时间热加载，不用重启；在线会话需要重新登录。

## 4. 发新版本

```powershell
# 1) 本地编出静态二进制（隧道插件会一起产出并复制到主程序旁边）
bash build-linux.sh dist              # 或 Windows 上 .\build.ps1

# 2) 两个文件都要传：主程序 + 插件。少了插件只是没有内建隧道
scp dist/cochat-linux-amd64 root@服务器:/tmp/
scp dist/libcochat-tunnel.so root@服务器:/tmp/

# 3) 装（安装脚本会校验架构，并把插件一起放进同一目录）
ssh root@服务器 "install -m 755 /tmp/cochat-linux-amd64 /tmp/cochat && \
                  install -m 755 /tmp/libcochat-tunnel.so /tmp/ && \
                  bash -s" < install.sh

# 4) 重启，拿新地址
ssh root@服务器 "cochat --res"
```

> 插件和主程序**必须同一目录**：loader 先找 exe 同目录，再找 `plugins/`。

`cochat --cur` 和 `--res` 在服务器上同样可用（systemd 托管的实例走 unit 重启）。

## 5. 出问题时的排查顺序

1. `cochat --cur` —— 实例还在吗？端口对吗？状态是哪个？
2. `cochat --passwd --check <用户> <密码>` —— 是登录问题还是别的问题？
3. 打开页面的隐藏排障面板（点 `#btn-diag`），看
   `连接状态 / 协商状态 / 本地流 / 远端流 / 画面尺寸 / ICE 候选对 / 收发字节`。
4. 通话不通看 [通话收发不了音视频-排查.md](通话收发不了音视频-排查.md)。
5. 实在不行 `cochat --res` 重起（会打印新地址）。

面板里几个关键读数：

| 读数 | 正常 | 异常含义 |
| --- | --- | --- |
| `连接状态: connected / connected` | 双向 ICE 已通 | 卡在 `connecting` 说明 NAT/防火墙挡住了 |
| `画面尺寸: 远端 640x480` | 解码出帧 | `0x0` 表示有轨道但没解出画面（应用会自动自救重开摄像头） |
| `远端播放: paused=false` | 在播 | `paused=true` 通常是被自动播放策略拦了，点一下"恢复声音" |
| `video 收 / 发` 字节数在涨 | 真的在传 | 不涨说明单向断了 |

## 6. 数据都在哪，什么会被删

| 路径 | 内容 | 谁写的 |
| --- | --- | --- |
| `~/.intercom/<用户>.json` | 账号：只存盐和 PBKDF2 哈希，**没有明文密码** | `--add` / `--passwd` |
| `~/.intercom/instances/<pid>.json` | 进程自述：端口、数据目录、原始命令行、cwd、对外地址 | 服务启动时写，正常退出时删 |
| `<数据目录>/ice.json` | 可选的自定义 STUN/TURN | 你手写 |
| `<数据目录>/admin-sessions.json` | 面板会话令牌（7 天过期）。**不含密码**，POSIX 上权限 0600 | 登录面板时 |

- 自述文件里**没有任何账号或密码信息**，只有"这个进程是怎么被启动的"。
- 面板会话文件被删掉不会丢数据，只是所有人要重新登录一次面板。
- 进程被强杀会留下自述文件；下次 `--cur` 会自动清掉死 pid 的残留。
- 聊天内容、语音、视频**只在双方内存**里转发，服务端不落盘、不入库。

## 7. 一批实例怎么管

一台机器上跑多个实例（不同端口、不同账号目录）是支持的：

```powershell
cochat --port 8080 --accounts D:\a --tunnel-url https://a.example
cochat --port 8081 --accounts D:\b --tunnel-url https://b.example

cochat --cur                      # 两个都列出来
cochat --cur --data D:\a          # 只看 a
cochat --res                      # 重启 pid 最小的那个
cochat --res <pid>                # 点名重启
```

`--res` 不带 pid 时故意只重启**一个**（pid 最小），不会一次把整机服务全掀了。
